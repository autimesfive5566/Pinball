# 需求基準

來源：使用者在本專案對話分段提供的「台灣夜市小鋼珠彈珠台模擬器」第 0～18 節，並於「已全部提供」後要求規劃。本文是保留需求意義的整理，不是逐字原文。後續明確的使用者修訂優先，須同步記錄。

## 1. 目前授權與開發順序

- 先完整分析技術、架構、物理風險、分階段工作與驗收，不直接實作完整遊戲。
- 先確認整體方案與 Phase 0 範圍，再逐步開發。
- 本次新增任務是建立可跨對話接手的文件，已明確授權直接建立及排除建立問題；不代表已開始 Phase 0。
- 文件與技術說明使用繁體中文。

## 2. 定位與優先順序

模擬台灣夜市「投入鋼珠 → 跑燈選倍率 → 停止 → 可繼續投入 → 拉桿發射一顆 → 落入亮燈球道得獎」的機械式小鋼珠彈珠台，不是一般 Pinball 或完整商業 Pachinko。

核心體驗：先確定倍率，再決定投入量，最後以一次實際發射承擔結果。

優先順序：真正透明的小型 Windows 視窗、60 FPS 目標、自然物理、正確規則、容易調整、極簡視覺。

本機單人、虛擬鋼珠，不涉及金錢、現金兌換或實體獎品。運行不需要網路、城市資料、地圖或定位。

## 3. 候選技術與依賴限制

首選 TypeScript、Tauri 2、Vite、Canvas 2D、Planck.js、WebView2，必要原生部分使用 Tauri API／Rust，目標 Windows 10／11。

這是首選而非不可調整的強制技術。先驗證 Tauri；只有合理排錯後仍有重大透明問題，才比較 Electron，不因方便就直接替換。

第一版不需要 Unity／Unreal、3D、React／Vue、後端、REST API、資料庫服務、帳號或複雜 UI 套件。新增依賴必須有實際理由。

## 4. 視窗與視覺

- 暫定 260 × 420 logical pixels，可因可讀性稍調整。
- Alpha 透明、無系統標題列／邊框／陰影、預設不置頂、不允許直接調整大小。
- 可適當拖曳、正常關閉及重新開啟；不能隱藏後無法找回。
- 空白 Canvas／HTML 區域能看到桌面或其他程式，不能用色鍵或假背景取代。
- 無白／黑底、明顯邊線殘影；圓形邊緣正常抗鋸齒；不加 Mica、Acrylic、毛玻璃。
- 視覺透明不等於滑鼠穿透；第一階段先正常操作，不整面強制穿透。
- 支援 125%、150% 等高 DPI，畫面坐標與物理坐標明確分離。
- 圓形鋼釘／球、線段球道、少量文字與必要按鈕；不需圖片、粒子、華麗燈框、背景板或複雜動畫。
- 倍率閒置時不顯示，跑燈一次顯示單一數字，停止後保留該數字。
- 必要資訊：餘額、投入、倍率、操作與結果。Debug 預設隱藏。
- 後續可有隱藏／恢復、置頂、系統匣、可停用／修改的全域快捷鍵。

## 5. 已確認遊戲規則

| 倍率 | 亮燈球道數 |
| --- | --- |
| 2 | 5 |
| 4 | 4 |
| 6 | 3 |
| 8 | 2 |
| 10 | 1 |

- 第一版固定 12 球道，由左到右編號 1～12，不需任意格數切換。
- 每局至少 1、最多 99 顆，不能投入超過餘額。
- 投入第一顆立即減餘額並開始跑燈；依 2→4→6→8→10→2 循環。
- 按停採當下顯示的倍率，不能背後另抽不一致的結果。
- 停止時確定倍率與燈位，之後加碼不改倍率及燈位。
- 發射後禁止加碼，一局僅一顆物理球，不是投入幾顆就發幾顆。
- 每投入一顆扣一顆；發射不能再次扣款。總餘額可超過 99。
- 中獎總返還 `reward = totalBet × multiplier`，不中為 0；不額外退本金。
- 核對公式 `balanceAfter = balanceBeforeRound - totalBet + reward`。
- 50 顆投入 10、6 倍：中獎後 100，失敗後 40；最大單局返還 990。
- 餘額不足一顆時需有清楚的結束／重新開始流程。
- 同時最多一顆球，禁止重複發射、結算、扣款及發獎；未確定倍率不能發射。
- 發射不足以入盤時允許原局重發，不算失敗、不重新收費。

## 6. 物理與公平性

- 球由槽底沿側邊實體軌道向上，經上方導流後進釘區，再自然落入球道。
- 發射力道影響初始速度，不能以固定路徑動畫替代物理。
- 動態圓球；固定圓釘、牆、軌道及隔板；獨立球道感測器。
- 重力、摩擦、彈性與碰撞自然改變球路，不能輕易穿透固定物件。
- 不需要完整 3D 滾動或學術級真實度；用有效向下重力近似斜面。
- 多排錯位釘板，座標、數量、尺寸及材質集中管理，可直接使用座標資料。
- 使用明確世界單位，不把 Canvas px 當公尺。
- 固定 dt；從 60 Hz 驗證，120 Hz 是待測選項，不是已定必要值。
- accumulator、追趕上限、必要的插值、CCD／bullet 均按實測決定。
- 卡球、抖動、弱發射及無效落點要有容錯，不得直接指定得獎格。
- 球道結果只一次，需處理首次接觸後彈回、交界、感測器位置與穩定確認。
- 最終落點決定輸贏，不預抽勝負，也不依倍率暗調球路。
- 不能假定每條落珠機率 1/12，或把亮燈數／12 直接當實際中獎率。
- 燈位產生與物理獨立；可統計各球道次數、不同力道及布局。
- 若有隨機參數須能設定種子；不要求跨平台或引擎版本浮點結果完全相同。
- 開發者大量發射工具不需出現在正式遊戲 UI。

## 7. 效能與生命週期

- 可見狀態以至少 60 FPS 為目標，必須實際量測並記錄環境。
- rAF 畫面與固定物理步進分離；避免每幀大量分配、重建靜態剛體、昂貴 DOM 更新。
- 可按需要離屏快取靜態圖形，不為尚未量測的問題預先複雜化。
- Debug 可顯示 FPS、frame time、physics step time、剛體數、phase、速度及最終 lane。
- 隱藏／最小化可暫停；恢復保留狀態、不追算整段停用時間、不跳球、不重複結算。

## 8. 未定項目與禁止誤認

以下尚未確認：真實釘子總數／位置、軌道形狀、材質、倍率權重、停止延遲、自動停燈、燈位特殊組合、各球道實際分布。

以下是需求書容許暫定、而非定死的項目：260×420、初始 100、跑燈速度、釘位與尺寸、物理係數、發射範圍、燈位抽法、輸入方式、60／120 Hz、快捷鍵與系統匣。

建議預設與待決策清單見 `DESIGN.md`、`STATUS.md`。未經新決策，不把隨機不重複燈位、80 根釘或退款規則說成真實機台特性。

## 9. 排除範圍與打包

不做 3D、複雜音效、精美素材、成就、排行榜、登入、雲端存檔、多人、支付、實體兌獎、多機台、造型、手機、自動更新或進階反作弊。

最終需 Windows 執行檔或安裝包、WebView2 需求處理、操作說明及發布前測試。開發版可執行不等於正式安裝包已驗證。
